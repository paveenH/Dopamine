
## 第二优先：可以整理，但要保留任务特性

5. **BBH Object Counting**
   - 数字输出，可以使用统一的 candidate-timing 指标。
   - 但要同时报告 degenerate/loop，避免把格式退化误读为行为改善。

6. **CRUXEval-O**
   - Bare 与 Chat 应分开。
   - 可整理 `early_candidate`、pre/post-marker length、valid submission、degenerate/truncation。
   - Python literal 输出和 marker 规则特殊，不能直接照搬 GSM8K 数字提取器。

7. **FinQA**
   - 可以统一 first/last、candidate timing 和 stopping。
   - 但必须突出它是自定义数字答案评分，不是官方 program execution。
   - Llama 的严重 loop/truncation 应作为解释前提。

## 第三优先：需要任务专属指标，不宜强行统一

8. **LogiQA 2.0**
   - 答案是 A–D，现有数字版 `early_candidate_rate` 不适用。
   - 应改用 task-native 指标，例如：
     - `native_answer_first_rate`
     - valid option submission
     - pre/post-answer characters
     - first–last option change

9. **ProofWriter-OWA**
   - 输出是 True/False/Unknown，重点应是：
     - valid submission
     - no-answer rate
     - conditional accuracy
     - multiple-answer/first–last disagreement
     - loop/truncation
   - 不建议强行套数字 candidate detector。

10. **ZebraLogic-Easy**
    - JSON/结构化答案，核心是：
      - valid JSON / complete answer rate
      - no-answer rate
      - puzzle accuracy
      - truncation
    - 不适合直接与 GSM8K 的 commitment timing 横比。

另外，两组可以暂时不进入统一整理：

- **Persona 实验**：保留为模型特异性的文本内容分析。
- **Willingness / confidence 自评**：作为失败的 manipulation check 简短保留，不必继续扩充指标。

建议实际执行顺序是：

> GSM8K → MATH → GSM-Hard → GSM-Symbolic → BBH → CRUXEval/FinQA → LogiQA/ProofWriter/ZebraLogic

前四个建立统一主指标体系；后面的任务主要用于检验适用边界，不必追求所有任务拥有完全相同的指标。
